# 探针脚本：`probe_layer1_fit.py` — 结果与结论

> **存档说明（2026-09）**：本文档及 `probe_layer1_fit.py` / `probe_report.json` 是算法重做前的探针档案，记录对真实户型数据的一次可行性验证。文中引用的 `RoomDecomposer` / `WallSegment` / `groups.json` 等代码已在算法重做中清理或迁入 `tools/`，本文档作为**历史数据结论**保留，不再与当前代码保证一致。结论仍是对「真实历史组合摆放结果 vs 几何约束」的有效观察。
>
> **术语**：本文档中的「组合布局」指「把 Group 摆进房间」这个算法任务本身，非被废弃的旧框架术语。

**目的**：数据量还不够训练 Layer 2 模型，但先确认"数据驱动布局"这条流程能不能跑通——真实历史组合布局结果（`converted/layout_samples/`）能否对接 xasset 现有几何约束基础设施（`RoomDecomposer`/`WallSegment`/`groups.json`），输入输出格式是否对得上。跑法：`python data/house/probe_layer1_fit.py`，输出 `converted/probe_report.json`。

> 注意区分概念：`WallSegment`/`depth_profile` 是**约束基础设施**（描述墙段几何），不是"组合布局方法"本身——`compose.py::HouseLayoutComposeStage` 目前 `placed_groups` 仍是空 stub，还没有任何方法能从空房间生成组合布局。本次探针是反过来验证：拿历史真实组合布局结果，检查它们在这套约束基础设施下会不会被判定为合法，用来提前发现"未来写候选生成逻辑时会踩的坑"。

## 结论一：流程本身跑通了，格式基本对上

- 73 条 resolved 样本、164 个 `placed_group`，**0 个 pipeline 异常，0 个格式适配问题**——房间几何能正确构造成 `SceneVector` 跑过 `SceneUnderstandStage` + `RoomDecomposer`，`layout_samples[].placed_groups[]` 的字段能顺利映射到 `PlacedGroup` 兼容结构。
- 唯一的字段差异是命名：源数据是 `rotation_yaw_deg`，`PlacedGroup` 是 `rotation`——语义/单位一致（都是绕 Y 轴角度，单位度），只是命名不同，探针脚本里做了显式重命名，没有静默转换。

## 结论二：一个真 bug（轴对齐方向搞反）+ 一个真的语义粒度问题

**先修的是一个脚本 bug，不是近似取舍**：初版 `_axis_align_size()` 认为 `size` 的 x/z 分量该不该交换取决于 `rotation_yaw_deg`（按最接近的直角把 w/d 换过来）。这个假设本身就是错的——`size` 是在物体自身的局部/摆放坐标系下记录的，`size[0]` 恒对应"沿墙方向"、`size[2]` 恒对应"朝房间深度方向"，这个对应关系与物体在世界坐标系里转了多少度无关。实测在 `rot≈±90°` 的样本上，初版逻辑系统性判反（例：`100902` 电视组 `rot=-90.001` 时 `size=[1.04,1.489,0.084]`，`0.084` 明明是贴墙的薄边该对应深度，初版却把它塞进宽度，反而拿粗大的 `1.04` 当深度去比，报"深度超限"）。**去掉轴交换、固定用 `size[0]→w, size[2]→d`**，尺寸检查 pass 从 64/144 直接跳到 105/144（73%）——证实这是实现错误，不是数据或规则的问题。

**修正后仍存在的、真实的粒度问题**：`groups.json` 的 `footprint_range` 描述的是**锚点角色（anchor object）本身**的尺寸（例：`code=100201`床组，`footprint_range[0]=[1.5,2.2]`，与同一 Group 定义里 `roles[bed].size_range.w=[1.5,2.2]` 数值完全相同），但 legacy 数据的 Group 级 `size` 是**整个 Group（锚点+所有子物件）的外包框**——这个粒度差异是真实的，不是 bug。剩余 39 条 fail 里能看出两种子物件排布模式：
- **两侧型**（床头柜挂在床两侧、餐边柜靠墙）——只撑宽度，深度基本不受影响，深度检查可靠。`100201`(床) 12 pass / 2 fail 就是这种情况。
- **环绕型**（餐椅围着餐桌四周）——宽度和深度都被子物件撑大，深度检查也不可靠。`100101`/`100102`(餐桌组) 深度分量普遍落在 1.7~2.45m，远超 `footprint_range` 给的 0.8~1.5m,**0 pass 全 fail**，原因是餐椅同时占用了桌子前后左右的空间,不只是两侧。
- 另外 `100701`(浴缸组) 8 条 fail 是另一种原因——同一个 code 混了"浴缸"和"壁挂花洒"两种真实尺寸差异巨大的家具（`obj_type` 不同），根源是 legacy 数据的分类粒度比 xasset 的 Group 粒度更细，不是子物件撑大的问题。

**这意味着**：真正实现 Layer 1 候选生成时,"深度分量能不能代表锚点尺寸"这件事**因 Group 类型而异**，不能一刀切地信任。判断依据大致是：子物件是否环绕锚点摆放（餐桌、书桌这类通常不可靠）还是仅贴靠两侧（床、柜类这类通常可靠）。如果未来素材库能提供锚点 object 单独的尺寸，这个问题能被根本解决；在那之前，只能按 Group 类型分别判断深度检查的可信度。

## 结论三：`wall_offset_ratio` 描述的是"沿深度方向从贴墙滑到对面墙"的连续轨迹，墙段关联逻辑要按它统一处理，不是只做"贴墙/不贴墙"二选一

初版用几何中心到墙的垂直距离 <0.3m（固定容差）判定"贴墙"，这个假设对薄型家具（柜子、马桶）没问题，但对进深较大的家具（床 d≈2m）系统性失效：贴墙摆放的床，几何中心到墙的距离本来就该 ≈ 半个床深（~1m），不是趋近于 0。初版因此把大量真实贴墙的床/书桌误判为"无匹配墙段"（`no_matching_wall` 80/144）。

第一次修正：改用 `footprint_range` 算出的期望半深度（`(d_min+d_max)/4`）作为容差基准。`no_matching_wall` 从 80→12，但这一版仍是"贴墙 or 不贴墙"的二元逻辑——`100101`/`100102`(餐桌组，`wall_offset_ratio=0.5`) 之类天然不贴墙的 Group，无论怎么调贴墙容差都测不出来，只能靠"承认这是预期内的无匹配"来解释,没有真正把它们关联到"最合适的 WallSegment"上。

**第二次修正（关键认识）**：`wall_offset_ratio` 不是"贴墙/不贴墙"的开关，是家具沿深度方向从贴墙(0.0)滑到房间对面(1.0)这条轨迹上的位置比例——`work`/`dining` 这类 `ratio>0` 的 Group，依然应该先关联到"最合适的 WallSegment"，只是最终落点沿着这段墙的深度方向往房间内推。于是把期望距离公式统一成：

```
expected = d_avg/2 + ratio × max(该点实际可用房间深度 D - d_avg, 0)
```

`D` 从候选墙段自己的 `depth_profile` 在对应投影位置取值，不再是脱离几何上下文的固定容差；`ratio=0` 时退化为"贴墙"，与第一次修正完全兼容。修正后 `100101`(餐桌组) 从"0 pass 全 0 匹配"变成 3 pass / 1 fail / 0 无匹配——用同一套关联逻辑就正确覆盖了这类居中摆放的 Group，不需要为它们单独写分支。

修正后剩余 15 条 `no_matching_wall` 里，深挖发现有 3 条（`100301`书房工作组）是**真实的数据现象，不是检查逻辑缺陷**：核对具体房间几何（如 `Library__9__0`，3.3×2.8m 矩形房间，工作桌位置 `(-3.91,-2.47)` 几乎正是房间几何中心），这几张历史真实数据里的书桌确实是悬浮在房间正中，完全没有贴任何墙——但 `groups.json` 把 `100301` 标注成 `wall_offset_ratio=0.0`（该贴墙）。这暴露出一个值得跟进的问题：小房间的书房工作组，历史设计里存在"贴墙"之外的真实摆放模式，`wall_offset_ratio` 目前是每个 Group 一个固定值，可能不够灵活到覆盖这种因房间条件（比如面积、形状）而变化的摆放策略。

**这意味着**：正式实现 Layer 1 候选生成时——(1) 贴墙候选的判定基准要来自 `footprint_range` 定义的深度，不是与家具类型无关的固定数值；(2) `wall_offset_ratio>0` 的 Group 不需要走独立于贴墙 Group 的候选生成路径，用统一公式即可；(3) `100301` 这类被观察到"贴墙"假设不总成立的 Group，需要决定是放宽约束、还是接受候选生成会漏掉这类历史摆法（本次探针发现的问题，留给正式实现前决策，不在这里改 `groups.json`）。

**追加发现：`100001`/`100002`(会客组) 的 2 条 `no_matching_wall`（`LivingDiningRoom__18__0`、`LivingRoom__28__2`）是同一类现象，且经过对全部 8 条"同房间有会客组+电视组"样本的核对，指向一个可靠的、非偶然的驱动因素——`facing_group`**：

逐段排查候选墙段（含门洞两侧的孤立短墙段、拐角对面段、乃至房间对面整段墙）后确认：门洞本身不能作为候选墙段（这本身是对的，门洞是硬性负选择），门两侧孤立的短墙段也够不到会客组的位置（跨度对不上），甚至房间对面那段最长的墙（`LivingDiningRoom__18__0` 里 edge=3，长 3.13m）虽然位置上几乎精确对上（`perp_dist≈2.267` 对 `depth_here≈2.230`，几乎贴到该墙能覆盖的最远处），但当前公式 `expected = d_avg/2 + ratio*max(depth_here-d_avg, 0)` 在 `depth_here < d_avg` 时会把 `max(...)` 钳到 0，导致这段本该成立的候选被判定为不匹配——这是公式在"该墙可用深度略小于 footprint 平均深度"这个边界情况下的钳位漏洞，跟"该不该建模 facing_group"是两件独立的事，不能混为一谈。

排除以上可能后，再核对全部 8 条同时有会客组（100001/100002）和电视组（100901）的样本：会客组与电视组的 `rotation_yaw_deg` 差值**8/8 全部恰好 180°**（严格正对，不是近似），中心间距在 2.06~3.00m 之间（数值不固定但都在"面对面留出活动空间"的合理范围）；同时电视组自己的贴墙检查 7/8 pass，说明电视组几乎总能可靠贴墙——真实驱动会客组位置的是"180° 正对着已摆放的电视组"，贴墙只是当电视组恰好贴在会客组对面墙时的伴生结果，两者分离时（进深够大的房间）会客组会脱离贴墙约束，径直摆到"正对电视组、间距在合理范围"的位置。这批数据里没有找到"会客组存在但同房间未放电视组"的样本（0 条），`facing_group` 不存在时的 fallback 行为暂无历史数据验证，但不影响上述结论——`wall_offset_ratio`（贴墙轨迹）和 `facing_group`（朝向另一已摆放 Group）是两条独立的、真实存在的摆放驱动逻辑，当前贴墙检查完全没有建模 `facing_group` 这条路径。跟 100301 一样，本次先记录，不改 `groups.json`，留给正式实现前决定。

**正式实现时的候选生成方案（已与用户讨论确认方向，未落代码）**：不需要新增"Zone 合并包围盒"的数据结构（会牺牲 Meeting/Media 各自独立的 tier/count/footprint 校验粒度），改为在候选生成层加一条"关系型定位"分支，按 `facing_group` 字段和该字段指向的 Group 是否已摆放来分流：
- `facing_group` 指向的 Group 已摆放 → 候选空间以该已摆放对象为参照系生成（`rotation = facing_placed.rotation + 180°`，沿其正面法线方向、`[min_gap, max_gap]` 距离区间内取候选），仍需过房间边界/碰撞的几何校验（Layer 1 不学习的部分不变）；
- `facing_group` 不存在，或该房间未摆放对应对象 → fallback 到现有 WallSegment 候选生成路径（`wall_offset_ratio` 公式）。

这个方案目前缺一个字段：`groups.json` 没有承载"面对面间距区间"的位置（8 条真实样本量出的 `[min_gap, max_gap]≈[2.06, 3.00]`），需要在正式实现前给 `facing_group` 配套加类似 `facing_gap_range` 的字段才能真正落地执行，本次只记录方案方向，不改 `groups.json`。

## 结果对比（初版 → 第一次贴墙判定修正 → 轴对齐 bug 修正 → wall_offset_ratio 统一化）

| 指标 | 初版 | +贴墙判定修正 | +轴对齐 bug 修正 | +wall_offset_ratio 统一化（最终） |
|---|---|---|---|---|
| 尺寸检查 pass / fail | 39 / 105 | 64 / 80 | 105 / 39 | 105 / 39（未变） |
| 贴墙检查 pass / fail / 无匹配墙段 | 59 / 5 / 80 | 114 / 18 / 12 | 114 / 18 / 12 | **115 / 14 / 15** |
| 格式适配问题 / pipeline 异常 | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |

（resolved 样本 73/128，placed_group 总数 164，其中 144 条有 group_code，详见 `converted/probe_report.json`）

最终尺寸检查通过率 105/144（73%）。剩余 39 条 fail 集中在 `100701`(浴缸/花洒混杂,8条)、`100902`(电视,5条)、`100101`/`100102`(餐桌,4+4条全fail)——都已在结论二里定位到具体原因（分类粒度混杂 / 环绕型子物件撑大深度），不是随机噪声。

最终贴墙/墙段关联检查通过率 115/144（80%）。剩余 14 条 fail **全部是 `depth_ok=True, length_ok=False`**——即匹配到的墙段深度够，但长度不足以放下该 Group 的宽度,这是干净的真实几何约束不满足信号，不再混有任何检查逻辑缺陷造成的假失败。剩余 15 条无匹配里 3 条对应真实的"该贴墙却未贴墙"历史数据现象（见结论三），其余是零星的房间边界情况。

## 已知局限（探针脚本本身，不是这次要解决的问题）

- 尺寸检查放弃了宽度维度的硬性判断——不是因为算错了，是因为宽度分量确实无法从 Group 级 size 里干净地拆出锚点 object 的宽度（结论二里"两侧型/环绕型"子物件排布的区分，本质上也说明深度分量并非对所有 Group 类型都可靠，只是相对宽度更可靠）。
- 墙段关联检查仍是启发式匹配（按 diff 最小选墙段），不是真正的候选生成/评分逻辑，也未处理"同一位置可能同时贴近两段墙"（比如凸角）之类的边界情况。
- 55 条 unresolved 样本没有房间几何，本次探针跳过未处理。
- 这仍然是探针脚本，不是可复用的候选生成代码；正式实现 Layer 1 时这里的逻辑需要重写为生产代码（比如恢复到 `xasset/` 包内、覆盖测试等），不能直接把探针脚本原样搬过去。
