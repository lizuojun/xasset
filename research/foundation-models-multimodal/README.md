## 0. 一句话结论

> **大模型擅长"语义与选择"，不擅长"精确几何与数值"；它真正的用法不是"让它一步给出最终答案"，而是"让它给出结构化意图 + 用确定性程序把意图落地"。**
>
> 这正好就是 Artist 范式「理解侧 × 约束侧」的行业依据——**这不是我们发明的，而是当前主流工程实践的共同结论。**

**机制层面的一句话**（详见 2.2 节）：

> **模型"看"图的方式，是把图片切成固定大小的格子（patch），每格压成一个"词"。**
> 格子就成了它视觉的最小分辨率——格子以下的信息，它根本没看见。
> 所以它能懂"这是什么"，但没法精确到厘米级坐标。

## 1. 主流模型的形态分类

理解"怎么借鉴"，先要分清现在有哪几类东西。它们的能力和用法完全不同：

| 类别 | 代表 | 核心能力 | 在 xasset 的定位 |
|------|------|---------|-----------------|
| **纯语言大模型** | GPT 系列、Claude 系列、DeepSeek、Qwen | 语义理解、推理、代码、结构化输出 | `understand`（文字路线）、`layout`（选候选） |
| **原生多模态大模型** | GPT-4o/5 系列、Gemini 系列、Claude 3.5+ | 图文联合理解、看图说话、粗略空间判断 | `understand`（图片路线的语义部分） |
| **视觉专用模型** | SAM 系列、Depth Anything、检测/分割网络 | 精确的像素级分割、检测、深度 | `understand`（图片路线的几何部分） |
| **结构化/约束解码** | outlines、guidance、各家的 JSON Schema 模式 | 保证输出语法 100% 合法 | **所有 Stage 的产物落地** |
| **嵌入/检索模型** | text-embedding、CLIP 类 | 语义相似度检索 | `layout`/`surface` 选资产、案例检索 |

> **关键认知**：这五类**不是替代关系，是协作关系**。xasset 的每个 Stage 内部，都是从这个菜单里按需挑部件组装——这正是"理解侧技术按场景选型"的含义。

## 2. 设计实现的关键机制（这一节是借鉴的核心）

### 2.1 结构化输出：从"求它输出 JSON"到"约束解码保证合法"

**演化过程**：

| 阶段 | 做法 | 问题 |
|------|------|------|
| 早期 | prompt 里写"请输出 JSON" | 经常带 markdown 代码块、字段名错、多出解释文字 |
| 中期 | Few-shot 示例 + 后处理正则提取 | 仍会失败，长输出容易截断 |
| **现在** | **Constrained Decoding / JSON Schema 模式** | 语法层面 100% 保证合法 |

**实现原理（值得理解）**：约束解码不是"生成完再检查"，而是在**每个 token 采样时**，把不符合当前 schema 状态的 token 概率直接屏蔽掉。比如 schema 要求下一个必须是 `"`，那除了 `"` 之外的 token 全部被 mask。

**对 xasset 的借鉴（非常重要）**：

- 我们已经有 `pydantic` 契约（`pipeline/schemas/`），但**现在只做了"生成后校验"**
- 应该升级为**"生成时就约束"**：把 pydantic model 转成 JSON Schema，喂给模型的 structured output 接口
- **收益**：LLM 输出的语法错误率从"偶发"降到"0"，校验门只需要管**语义合法性**（如多边形自交），不用管语法

```python
# 借鉴方向：契约直接驱动结构化输出
schema = UnderstandOutput.model_json_schema()   # pydantic → JSON Schema
response = provider.generate(request, response_format={"type": "json_schema", "schema": schema})
output = UnderstandOutput.model_validate_json(response.content)  # 双保险
```

> **注意边界**：约束解码保证的是**语法合法**，不保证**语义/几何合法**。多边形是不是自交、开口是不是落在轮廓上，它管不了——这仍然必须由校验门负责。

### 2.2 他们到底是怎么"看"图的（实现机制拆解）

这一节回答"原生多模态模型是怎么做到的"。理解了这个机制，就能准确推断它能做什么、不能做什么。

**关键论文依据**：
- ViT: *"An Image is Worth 16x16 Words: Transformers for Image Recognition at Scale"* (Dosovitskiy et al., ICLR 2021, arXiv:2010.11929) —— 标题本身就是核心思想
- LLaVA: *"Visual Instruction Tuning"* (Liu et al., NeurIPS 2023 Oral, arXiv:2304.08485) —— 开源多模态的经典架构

#### 第一步：把图片"切块"成 token

**核心思想**：Transformer 只吃序列，那就把图片变成一个"词序列"。

```
一张 1024×1024 的图片
   ↓ 切成 32×32 像素的小块（patch）
   ↓
32 × 32 = 1024 个小块
   ↓ 每一块用一个向量表示（这就是"视觉词"）
   ↓
得到一个长度 1024 的序列 → 直接喂给 Transformer
```

> ViT 论文标题 "An Image is Worth 16x16 Words" 说的就是这个：**一张图等于若干个"词"**。原始 ViT 用 16×16 的 patch，当前商用模型（如 OpenAI 的）已演进到 **32×32**。

**为什么切块大小如此关键**：切块越小，保留的细节越多，但 token 数量暴涨（成本平方级上升）。切块越大，成本低但细节丢失。**这是一个必须权衡的工程取舍。**

**这直接决定了精度上限**：
- 1024×1024 的户型图，32×32 patch → 每个 patch 对应 32 像素
- 如果这套户型实际是 10m × 10m，那么 1024 像素 ≈ 10m，**32 像素 ≈ 31 厘米**
- 也就是说：**模型"看到"的最小单位就是约 31cm×31cm 的一块**。它无法区分相差 10cm 的边界位置

这就是"不能让它吐精确坐标"的**物理原因**，不是模型不够聪明，是**信息在这一步就被量化了**。

#### 第二步：用 Vision Encoder（通常是 ViT）提取特征

每个 patch 通过一个线性投影变成向量：

```
patch (32×32×3 像素)  →  展平成一维  →  线性层投影  →  一个 D 维向量
```

**patch 之间没有位置概念**——所以必须额外加上**位置编码**（positional embedding），告诉模型"这个 patch 在原图左上角"。

> 这也是另一个精度损失的来源：位置编码是离散的网格坐标，不是连续值。

#### 第三步：把视觉 token 接进语言模型

这里有两条主流路线，正是上次讨论的"原生 vs 适配器"：

| 路线 | 做法 | 代表 | 特点 |
|------|------|------|------|
| **适配器（后期融合）** | ViT 输出 → **一个投影层（MLP/Q-Former）** → 变成 LLM 的 token 空间 → 和文本 token 拼接 | **LLaVA** | 架构清晰、易实现、开源方案多 |
| **原生（早期融合）** | 视觉 token 与文本 token **从第一层就同处一个 Transformer**，联合训练 | GPT-4o/5、Gemini | 跨模态理解更强、更自然 |

**LLaVA 的具体做法（可直接参考的开源方案）**：
1. 用预训练的 **CLIP ViT** 作为视觉编码器（已在大规模图文对上训练过，语义能力强）
2. 加一个**线性投影层**，把视觉特征映射到语言模型的词向量空间
3. 把投影后的视觉 token 和文本 token 拼成同一个序列
4. 在指令数据上微调，让它学会"看图后按指令回答"

> LLaVA 论文的关键贡献之一，是用**纯语言 GPT-4 自动生成多模态指令数据**（把图片的描述和框转成对话），解决了多模态指令数据稀缺的问题。

#### 第四步：解码时坐标怎么出来

当模型要输出 `"x": 3.75` 这样的坐标时，它是**逐字符生成**的：

```
"x"  →  ":"  →  " "  →  "3"  →  "."  →  "7"  →  "5"
```

每一步都是从一个离散词表里选一个 token。**这不是数值回归**。所以：

- 模型不能在两个 token 之间"插值"
- 小数位数越多，累积的离散化误差越大
- 它判断"3.7"还是"3.8"本质上是一次**分类**，不是连续量的估计

**这就是"坐标用离散 token 表示"的含义**，也是精度不如专用回归模型（如检测网络的 bbox 头）的根本原因。

#### 第五步：那为什么它还能"看起来很懂"？

因为它懂的是**语义和常识**，不是**度量**：

| 它能做得好的 | 底层原因 |
|-------------|---------|
| "这是卧室" | patch 组合出的视觉特征与语言中的"卧室"概念对齐 |
| "床在房间左侧" | 位置编码 + 注意力机制能捕捉相对空间关系 |
| "这个布局不合理，床挡住门了" | 常识推理，语言模型的核心能力 |
| 认出门、窗的图标 | 视觉特征匹配，不需精确坐标 |

| 它做不好的 | 底层原因 |
|-----------|---------|
| 精确多边形顶点 | patch 量化 + 坐标离散 token |
| 精确距离/尺寸 | 无绝对尺度参照，且数值精度不足 |
| 精确计数（如"7 个房间"） | 官方文档明确承认"may give approximate counts" |
| 精细空间定位 | 官方文档明确承认"struggles with precise spatial localization" |

---

**为什么会这样（实现层面的原因）**：

1. **视觉编码器的分辨率损失（有官方数据可查）**：图像被切成 patch 压成 token。以 OpenAI 官方文档为例，当前主流模型是 **32×32 像素一个 patch**。一张 1024×1024 的图 = 32×32 = 1024 个 patch ≈ 1229 tokens。**在 1024 的图上，一个 patch 对应 32 像素——如果这张图是一套 10m×10m 的户型，32 像素 ≈ 31 厘米。这就是坐标精度不足的物理根源。**
2. **坐标用离散 token 表示**：模型输出 `"x": 3.75` 时，是在逐字符生成，不是真正在回归一个连续值
3. **缺少绝对尺度**：一张房间照片，模型不知道这是 3 米还是 30 米

> **官方明确承认这是限制**（引自 OpenAI 模型文档 Limitations 节原文）：
>
> - *"**Spatial reasoning**: The model struggles with tasks requiring precise spatial localization, such as identifying chess positions."*
> - *"**Counting**: The model may give approximate counts for objects in images."*
>
> 这两条几乎逐字对应我们最需要的能力——**精确空间定位**和**精确计数**，恰恰是官方标注的弱项。

**分辨率档位（`detail` 参数）—— 直接决定能干什么**：

| 档位 | 行为 | 适合 xasset 的哪一步 |
|------|------|---------------------|
| `low` | 压缩到 ~512×512 | 只够判断"这是什么场景" |
| `high` | 最多约 2500 patch | 判断房间数量、大致关系 |
| `original` | 保留原分辨率（上限约 30000 patch） | **坐标敏感任务**（OCR / 小目标检测） |

官方明确建议：*"For tasks that require fine visual detail or **precise coordinates**, such as OCR, small-object detection, or computer use, use `detail: original`."*

> 但即便用 `original`，精度仍受 patch 量化限制——**它是"更准"，不是"精确"**。

**对 xasset 的借鉴 → 这正是"理解侧 × 约束侧"分工的硬依据**：

```
图片输入
  ├─ 语义部分（什么房间、什么关系）  → 多模态大模型（强项，high 档足够）
  └─ 几何部分（边界在哪、开口在哪）  → 视觉专用模型（SAM 分割 / 检测 / 深度）+ 几何后处理
                                        ↓
                                   约束侧：多边形拟合、正交化、闭合、尺度推断
```

**绝不能让多模态大模型直接吐房间多边形坐标**，这是它最不可靠的地方。

### 2.3 视觉 Grounding：模型如何"指出"位置

如果需要模型指出位置，主流做法不是让模型输出坐标，而是：

| 方式 | 做法 | 精度 | 实现本质 |
|------|------|------|---------|
| **边界框回归** | 模型输出 `[x1, y1, x2, y2]` 归一化到 0~1 | 中等，常用于"大致在哪" | 原生多模态内建 |
| **点标注 / Point prompting** | 输出一个归一化点坐标 | 中等 | 原生多模态内建 |
| **调用检测工具** | 模型调用一个专门的检测 API（function calling） | **高**，因为实际是专用模型在算 | **Agent 编排** |
| **返回 mask / segmentation** | 部分模型支持直接输出分割 | 高，但接口不统一 | 原生 + 专用混合 |

**对 xasset 的借鉴**：

- 用大模型做**"发现与调度"**：让它判断"这张图是户型图还是实景照""需要调用哪个检测器"
- 用**专用模型做精确切割**：SAM 出 mask，再用几何算法拟合多边形
- 大模型给出的边界框只能用于**初始定位 / 裁剪区域**，不能当最终几何

### 2.4 从 Agent 视角看：多模态能力到底是怎么实现的

这是设计理解侧时最需要想清楚的一个问题。**"这个大模型有多模态能力"这句话，实际上可能是三种完全不同的东西**：

| 实现方式 | 本质 | 典型表现 | 对 xasset 的意义 |
|---------|------|---------|-----------------|
| **A. 原生多模态** | 视觉编码器 + 统一 Transformer，图像 patch 与文本 token 同处一个序列 | 能描述图片、回答问题，但精度受 patch 量化限制 | 适合做**语义判断**，不适合精确几何 |
| **B. Agent 编排（LLM + 工具）** | LLM 本身不看图，或只看粗粒度图；它**调用外部视觉工具**完成实际计算 | 能调用检测 API、分割 API、OCR API | 适合做**调度与决策**，精度由工具决定 |
| **C. 视觉模型 + 文本提示** | 模型本身是视觉模型（如 SAM 类），用文本/点作为提示 | 精确分割、精确检测 | 适合做**精确几何提取** |

**关键认知：这三者不是替代关系，而是可以叠加协作。**

一个现实的 Agent 应用架构通常是 **B 包着 A 和 C**：

```
用户请求（图片）
    ↓
LLM（调度器，可以是纯语言模型）
    ├─ 判断：这是户型图/实景照/概念图？        ← A 或纯语言模型
    ├─ 调用：SAM 分割出区域 mask              ← C（专用视觉模型）
    ├─ 调用：检测模型找出门窗                  ← C
    ├─ 调用：OCR 读取尺寸标注                  ← C
    └─ 汇总：语义结论（几室几厅、什么关系）     ← A（多模态大模型）
    ↓
约束侧：几何后处理 + 合法性校验
```

**所以对 xasset 的正确认知是**：

- **理解侧不是"一个模型"，而是一个"能力组合"**
- 你不需要找"一个什么都能干的多模态大模型"——**它不存在**
- 你需要的是：**用 LLM 做编排，把语义判断交给多模态模型、把精确几何交给专用视觉模型、把合法性交给约束侧**

> 这也解释了你观察到的现象："很多大模型有图像识别、分割能力"。**多数情况下，那不是模型自己在做分割，而是平台在背后接了专用视觉模型。** 少数情况下（如某些模型的多边形/mask 输出能力）确实是原生支持，但精度与专用模型仍有差距。

### 2.5 多模态融合方式的技术分类

| 方式 | 含义 | 代表 |
|------|------|------|
| **原生多模态（早期融合）** | 图像 patch 和文本 token 一起进同一个 Transformer | GPT-4o/5 系列、Gemini |
| **后期融合（适配器）** | 视觉编码器 + 投影层 + 语言模型 | LLaVA 类开源方案 |
| **工具编排（不融合）** | 大模型作为调度器，实际计算交给专用工具 | Agent 类方案 |

**对 xasset 的借鉴**：

- 走**工具编排**路线比"期望一个大模型全包"更现实
- 理解侧不必是"一个模型"，可以是**"大模型做调度 + 多个专用模型做计算"的组合**
- 这与 Artist 的"两侧技术按场景选型"完全契合——**理解侧内部本身也可以是多部件编排**

### 2.6 上下文与长文本能力的实际消耗

**重要成本认知**：

- 图像 token 消耗远大于文本。一张图可能消耗几百到几千 token，高分辨率更高
- 多图输入（如一个户型的多张照片）成本线性上升
- 长上下文（如把整份 SceneVector 塞进去）也会显著推高成本

**对 xasset 的借鉴**：

- **不要整包塞数据**。`understand` 给模型的应该是**摘要 + 必要片段**，不是完整场景数据
- `layout` 需要知道区域边界，但不需要知道每个顶点的精确坐标——可以给**简化的多边形 + 面积 + 关键尺寸**
- 各 Stage 的 prompt 应该"最小必要信息"，这也符合 2.2 节说的"只让它做语义判断"

## 3. 映射到 xasset 的六个 Stage

### 3.1 总体分工建议

| Stage | 理解侧候选 | 约束侧必须做什么 | 关键注意 |
|-------|-----------|----------------|---------|
| `understand`（文字） | 语言大模型 | 词表校验、区域非空、关系自洽 | 用 structured output 直接产 `UnderstandOutput` |
| `understand`（图片） | 多模态大模型（语义）+ SAM/检测（几何） | 多边形拟合、闭合、正交化、尺度推断 | **大模型不产坐标** |
| `geometry` | 几何/视觉重建算法 | 多边形合法性、开洞落边 | 这里几乎不需要大模型 |
| `layout` | 大模型选候选 / 打分模型 | 碰撞、净宽、越界求解 | 让它"选"，不让它"算坐标" |
| `surface` | 大模型/检索做材质语义匹配 | 覆盖完整性、归属合法 | 语义匹配是强项，合适 |
| `accessory` | 大模型选点缀类型 | 在区域内、不挡通道 | 同上 |
| `stylize` | 大模型选风格组合 | 参数区间、词表合法 | 强项，适合 |

### 3.2 三个具体可落地的技术点

**技术点 1：契约驱动的结构化输出（所有 Stage 通用）**

```
pydantic model → model_json_schema() → 模型 structured output 接口 → model_validate_json()
```

- 现状：我们只有后两步（生成后 validate）
- 改进：加上 structured output 约束，语法错误率归零
- 代价：需要模型/框架支持 JSON Schema 模式（主流云服务都已支持）

**技术点 2：图片路线的"语义-几何分离"**

```
图片
 ├→ 多模态大模型：这是户型图/实景照？什么场景？几个房间？什么关系？   （只要文字结论）
 └→ 视觉专用模型：分割出区域 mask → 几何算法拟合多边形             （要精确几何）
```

- 融合点：大模型给出的房间数量/关系作为**约束**，约束侧的多边形必须满足这些约束
- 这天然就是"两侧迭代收敛"的一个实例

**技术点 3：大模型做候选筛选而非坐标生成**

`layout` 的正确用法：

```
❌ 错：给模型区域边界，让它输出沙发坐标 (x, y, z)
✅ 对：约束侧先用几何算法枚举合法候选位置 →
       大模型在候选列表里选"哪个最符合描述" →
       约束侧再校验选中的是否真的合法
```

- 这正好对应研究里 `learned-layout` 曾讨论的"约束编码进候选生成"思路
- 大模型只做**离散选择**，把连续数值计算留给程序

## 4. 能力边界速查表（写 prompt 时对照）

| 你想要的 | 大模型可靠度 | 建议做法 |
|---------|-------------|---------|
| 语义分类（这是什么） | ⭐⭐⭐⭐⭐ | 直接用 |
| 关系判断（相邻/包含/朝向） | ⭐⭐⭐⭐ | 直接用，但要给出明确的关系词表 |
| 风格/材质选择 | ⭐⭐⭐⭐⭐ | 直接用 |
| 从离散候选里选一个 | ⭐⭐⭐⭐ | 直接把候选列表给它 |
| 粗略位置（大致在哪一侧） | ⭐⭐⭐ | 只用于初筛 |
| 边界框（归一化坐标） | ⭐⭐⭐ | 只用于裁剪定位 |
| 精确多边形顶点 | ⭐ | **不要用**，改用分割+几何算法 |
| 精确尺寸/距离 | ⭐ | **不要用**，改用尺度推断算法 |
| 保证 JSON 合法 | ⭐⭐⭐⭐⭐ | 用 structured output |
| 保证几何合法 | ⭐ | 校验门负责，不是模型的活 |

## 5. 对当前设计的两处修正建议

### 建议 1：契约层增加"JSON Schema 导出"能力

现在 `pipeline/schemas/` 是 pydantic model，已经有了 `model_json_schema()`。建议：

- 在各 Stage 的 prompt 构建处，把 output_type 的 schema 一并传给模型
- 在 `LLMRequest` 上加 `response_schema` 字段（当前只有 `schema` 描述，但没有强制约束）

### 建议 2：`understand` 图片路线明确拆分语义与几何

当前文档写了"图片 → 视觉算法"，但没写清楚**多模态大模型在图片路线里的角色**。建议明确：

- 多模态大模型负责：场景类型判断、区域数量与关系、图文一致性校验
- 视觉专用模型 + 几何算法负责：精确轮廓
- 两者的产物在约束侧汇合
