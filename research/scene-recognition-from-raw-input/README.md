# 原始输入 → SceneVector：RecognitionService 技术路线调研

**日期**: 2026-08-06
**状态**: 方案讨论中（未落代码）
**问题**：`scene_understand` 之前缺一层——把 C 端用户能提供的原始输入（图纸/照片/文字/手绘）转成 pipeline 消费的统一 `SceneVector` JSON。这一层被称为 `RecognitionService`，定位是 pipeline **外部**的独立服务，不进 Stage 链，目前完全未实现。
**面向对象**：一般 C 端用户，不依赖专业设备（CAD 图纸、LiDAR 扫描仪、GIS 数据）。
**设计原则**：对用户的输入要求要足够简单——一次性提供单份素材（一张图/一段话/一张照片）即可，不要求用户做额外测量、多轮交互标注、或补充参照物。识别精度不足时，应该用模型自身的统计先验/合理性假设去兜底，而不是把负担转嫁给用户多做一步操作。这条原则贯穿全文档的路线取舍。
**文档边界说明**：本文档专注**原始输入识别（understand 层）**的三大类输入路线技术选型调研 + 相关工作文献综述——术语按 [unified-scene-pipeline](../unified-scene-pipeline/README.md) 的 Artist 术语表（轮廓 → 主体 → 细节，LLM × 边界约束）。产品形态设计（约束校验强制默认、自然语言编辑闭环、结果可视化对照、schema 现状分析等架构性结论）已收拢至该文档（唯一的架构决策权威来源），本文档不再重复。

## 0. 现状与目标格式

`SceneUnderstandStage`（`xasset/pipeline/stages/understand/scene_understand.py`）只认 `PipelineInput.scene_vector: dict`。这份数据现在的唯一来源是人工手写常量（`products/cli/debug_run.py`）或离线转换脚本（`data/house/convert.py`，把历史项目 `ihome-layout` 的数据转成同样格式）。`PipelineInput` 里已经预留了 `input_type: "text"|"image"|"concept_art"`、`text_description`、`image_url` 字段，但没有任何代码消费它们——这就是本文档要填的空白。

目标格式（以 house 为例，参见 `data/house/converted/rooms/*.json`）：

```json
{
  "region_type": "living_dining_room",
  "boundary": [[x, z], ...],
  "area": 26.44,
  "height": 2.6,
  "doors": [{"id": "...", "pts": [[x,z]*4], "to_room": "...", "door_type": "swing|sliding"}],
  "windows": [{"id": "...", "window_type": "normal|bay", "pts": [...], "sill_height": ..., "height": ...}],
  "structural_edges": [...]
}
```

三种 `scene_type`（house/urban/wild）在 `understand` 层名义上共用同一套 `SceneUnderstandOutput`/`SceneRegion` 抽象骨架，但目前只有 house 填满了这个抽象——逐字段分析和缺口结论见 [unified-scene-pipeline 第 2.1 节](../unified-scene-pipeline/README.md)（该分析是 layout / geometry 等后续 Stage 的阻塞项，不是 understand 专属问题，故归入架构文档统一维护）。

"区域轮廓识别"具体识别哪些对象，按 `scene_type` 各不相同——这也是三大类输入路线（第 2 节起）最终要收敛输出的语义粒度：

| scene_type | 识别对象 | 对应 SceneVector 字段 |
|-----------|---------|----------------------|
| house | 房间边界、墙、门、窗 | `boundary` / `structural_edges` / `doors` / `windows`（后三者是**轮廓语义**在 house 下的具体字段，见 [unified-scene-pipeline 术语表](../unified-scene-pipeline/README.md)） |
| urban | 道路网络、地块（花园/建筑基底）边界 | `boundary`（按 region_type 区分道路/花园/建筑基底），**轮廓语义**（路网出入口、用地红线等）字段语义见 [unified-scene-pipeline 2.2 节](../unified-scene-pipeline/README.md) |
| wild | 山体、水体、草地等地形特征区域边界 | `boundary`（按 region_type 区分地形特征类别） |

house 已经有完整定义（`ROOM_IMPORTANCE`/`_ROOM_TYPE_PRIORITY_MAP` 等，见 `scene_understand.py`），urban/wild 的 `region_type` 词表和字段语义目前完全空白，见 [unified-scene-pipeline 第 2.1 节](../unified-scene-pipeline/README.md) 的详细分析。

**轮廓之后的"细节"由现有 pipeline 六层继续完成，不属于 RecognitionService 范畴**：`geometry` 层做**边界几何重建**（把轮廓拉成真实几何：厚度、高度），`layout` 层做**组合摆放**（在区域内部摆放各类 Group），`surface`/`accessory`/`stylize` 负责材质、点缀、渲染风格。RecognitionService 只需要保证轮廓"大致对、几何合法"，不需要也不应该在这一层就把细节做实。

也就是说，三条路线的输出不是"最终答案"，而是一份**可编辑的初稿**——识别算法只需要把语义搭对（区域数量、大致形状、门窗大致位置），几何精修交给后续的约束校验和用户的自然语言调整来完成。这个思路把"识别准确率"的压力，从算法侧一部分转移到"约束校验 + 人工可控的二次调整"上，三大类路线的技术选型标准也随之改变：**不是选精度最高的模型，而是选"能快速产出语义正确的初稿"的模型**。

## 1. 相关工作：业内是否有类似实践

> 以下基于已有知识整理，非实时检索结果（当前环境 WebSearch 不可用），细节和最新进展建议后续联网核实。

[unified-scene-pipeline](../unified-scene-pipeline/README.md) 确立的"生成粗轮廓 → 约束校验 → 自然语言精修"Artist 思路不是新发明，学术界和产品界都有对应先例，但按方法论细分，没有看到与该文档设想的**Stage 清晰解耦、约束校验作为独立通用模块服务任意输入路线**这一具体架构完全对标的公开案例：

| 类别 | 代表工作 | 与统一架构思路的关联 |
|------|---------|-------------------|
| **文字→结构化布局生成** | LayoutGPT（NeurIPS 2023） | 用 LLM 把文字描述转成结构化布局（类 CSS），生成后可迭代精修，思路上与"文字→结构化矢量"一致 |
| **文字→3D 场景 + 约束求解** | Holodeck（AI2, 2024） | 文字描述生成完整房屋场景，内部有房间划分 + 约束求解（家具不重叠、门口留通行空间），与统一架构的"约束校验"高度重合，但约束是**生成过程内嵌**的优化步骤，不是事后独立校验层 |
| **生成-校验-修正循环** | I-Design | LLM 做室内设计，分阶段生成候选布局 + 约束检查 + 迭代优化，是"生成→校验→修正"循环的典型代表 |
| **场景生成 + 自然语言编辑** | SceneTeller / InstructScene | 文字驱动 3D 场景生成，支持后续自然语言指令做场景编辑（挪动/替换物体），把"自然语言二次调整"当作独立能力单独建模，思路一致 |
| **场景的结构化语言表达** | Meta SceneScript | 把场景表达成一种结构化语言（类似 SceneVector 的定位），生成模型直接输出这种语言化描述，与"矢量作为通用中间表达"的理念一致 |
| **约束驱动生成（前深度学习时代经典源头）** | Merrell et al., *Interactive Furniture Layout Using Interior Design Guidelines*（SIGGRAPH 2011） | 用一套设计准则（约束）驱动布局优化，确立了"约束 = 硬性规则库，生成 = 在约束下搜索/优化"的范式，是校验层思路的经典源头 |
| **像素级生成后自然语言编辑（图像领域，非矢量）** | InstructPix2Pix / Prompt-to-Prompt | "生成后用自然语言编辑"思路已经很成熟，但作用对象是像素图像，不是结构化矢量数据——本文档要做的是矢量级编辑，技术路径不通用，仅作理念参考 |
| **产品界** | 酷家乐（群核科技）、三维家等室内设计 SaaS | 近两年上线"AI 一键生成户型/软装" + 对话式调整功能，公开资料显示流程大致是"生成初稿 → 对话微调"，但约束校验细节不公开，是否有显式几何合法性校验层不确定 |

**结论**：核心思路本身有大量学术和产品实践佐证可行性，但"约束校验作为独立通用模块、服务于三大类输入路线"这个具体架构切法目前没有直接对标——多数现有工作把约束校验内嵌在生成过程里，而不是抽成一个可复用的独立校验层。这意味着方向上可以放心推进，但架构细节需要自己摸索验证，不能直接照搬某个现成方案。

## 2. 三大类输入路线

按输入形态分三大类，对应用户实际能提供的原始素材：

| 类别 | 输入形式 | 适用 scene_type | 核心难点 |
|------|---------|-----------------|---------|
| **A. 结构化图纸（含手绘草图）** | 户型图截图/拍照、手绘平面草图 | 主要是 house，urban 的规划草图也适用 | 图纸有规范符号体系但拍摄/手绘导致噪声、透视畸变 |
| **B. 自然语言描述** | 用户文字描述场景需求 | house/urban/wild 通用 | 语言天然模糊、欠约束，需要合理性兜底 |
| **C. 通用图片** | 手机照片、实景照片、概念图 | house/urban/wild 通用 | 缺深度/尺度信息，遮挡、光照干扰 |

---

## 3. 类别 A：结构化图纸（含手绘草图）

### 3.1 问题特点

户型图（无论是印刷体的中介 App 截图，还是用户手绘草图）都有**规范的符号语言**：墙用线段/双线表示，门用弧线+缺口，窗用双细线，还常常带有尺寸标注文字。这与"通用图片"的本质区别是——图纸本身已经是一种**矢量语义的 2D 编码**，识别任务是"解码"而非"从像素猜测三维语义"。手绘草图是这一类的退化版本：符号语言不规范（用户自定义画法），但空间意图（房间划分、门开位置）仍然明确。

### 3.2 技术路线

| 方法 | 技术要点 | 适用子场景 |
|------|---------|-----------|
| **专用目标检测/分割模型**（如基于 Mask R-CNN / U-Net 的 wall-door-window 检测，CubiCasa5k 数据集训练的模型） | 端到端语义分割墙体/房间区域 + 符号检测（门/窗/楼梯图标分类） | 印刷体户型图，符号规范、噪声小 |
| **CubiCasa5k pipeline**（Kalervo et al. 2019，经典基线） | 多任务网络：房间分割 + 图标检测 + junction 检测，三头输出后按几何规则重建墙线拓扑 | 户型图矢量化的事实标准 baseline |
| **OCR（PaddleOCR / 通用文字检测）** | 识别图上的尺寸标注（如 "3600" mm、"3.6m"），把标注数值关联到最近的墙段，校正检测出的几何比例尺 | 印刷体户型图（有标注文字），手绘草图通常没有精确标注，此步可跳过 |
| **几何后处理（墙线拟合/角点吸附/正交化）** | 检测输出是像素级 mask/框，需要拟合成直线段、吸附到网格、修正非正交误差 | 所有子场景，是从"识别结果"到"合法矢量"的必经步骤 |
| **Sketch-to-vector（草图专用）** | 手绘线条抗噪更弱，通常先做线条简化/去抖（如 RDP 简化），再用轻量分割网络识别房间连通区域；门窗位置由模型直接识别（不引入额外人工标注步骤，人机协同标注属于"额外交互"，与简单输入原则冲突，仅作为识别置信度过低时的可选兜底，不作为默认路径） | 手绘草图 |

### 3.3 与 OCR 融合的整体流程

```
图片输入
  → 预处理（去噪、透视校正、二值化）
  → 并行：
      a) 分割/检测模型 → 房间区域 mask + 门窗图标框 + 墙线 junction 点
      b) OCR 文字检测 → 尺寸标注文本 + 位置
  → 融合：用 OCR 数值校正检测几何的真实尺度（像素→米）
  → 几何后处理：墙线拟合、角点吸附、正交化、闭合多边形
  → 输出 SceneVector（boundary/doors/windows/structural_edges）
```

### 3.4 关键挑战

- 印刷体户型图的**画风差异**巨大（不同中介 App 的图标符号不统一），单一模型泛化性存疑，可能需要按数据源做风格归一化预处理，或用大规模多源数据训练
- 手绘草图**缺乏精确尺寸**，不能要求用户额外输入参照物测量（违反简单输入原则），应改为用统计先验兜底比例尺——如按识别出的常见家具/门宽（标准门宽通常 0.8~1.0m）反推比例尺，或按房间类型的常见面积区间做粗略校正
- 门窗的**朝向/开合方向**图标本身可能不含此信息，检测模型需专门学习该符号的方向语义

## 4. 类别 B：自然语言描述

### 4.1 问题特点

文字描述是**欠约束**的输入——"三室两厅，主卧带卫生间，客厅朝南"这类描述完全不含几何坐标，需要生成式模型同时完成"合理性推断"（房间数量/面积配比符合常识）和"几何落地"（把描述转成具体多边形坐标）两件事。这与图纸/图片路线的本质区别是：**没有可识别的原始几何证据，输出的矢量数据本身就是一次生成而非识别**。

### 4.2 技术路线

| 方法 | 技术要点 | 成熟度 |
|------|---------|-------|
| **LLM + 结构化输出（JSON Schema / Function Calling）** | 让 LLM 直接输出符合 `SceneVector` schema 的 JSON；用 constrained decoding（如 outlines / guidance / OpenAI structured output）保证语法合法性 | 工程上最成熟，各大模型 API 都原生支持 |
| **两阶段：LLM 生成 bubble diagram → 几何求解器落地坐标** | 先让 LLM 输出房间列表 + 关系图（连接/相邻/朝向约束），再用专门的布局求解器（如约束满足/优化算法，参考 Graph2Plan 的图→矢量解码器）把图转成具体多边形 | 几何合理性更有保障，工程复杂度更高 |
| **端到端布局生成模型（HouseDiffusion 等）+ 文本条件** | 把文字描述编码为条件向量，驱动扩散模型直接生成房间边界框，属于研究前沿，尚无成熟开源方案直接支持中文自然语言输入 | 研究阶段，工程化程度低 |

> **辅助策略（非独立路线）**：以上任一方法生成结果后，都可以用文字描述检索最相似的已有真实户型（如 `data/house/converted/` 里的 99 户型）做参数化改写或结果校正，降低生成的不合理概率。这是一个可叠加在任何技术路线之上的兜底手段，不是与上述三种并列的技术路线。

### 4.3 关键挑战

- **几何合法性**：LLM 直接吐坐标容易出现自相交多边形、门开在墙角外等非法几何，必须有强制的后校验/修复层（复用 `pipeline/utils/vector_normalize.py` 的去噪/归一化逻辑）
- **欠约束的多解性**：同一句描述可以对应无数种合理布局，产品上需要决定是"生成一个确定结果"还是"生成多个候选让用户选"
- **跨 scene_type 的语义差异**：house 描述里的"朝南"是房间朝向，urban 描述里的"沿街商铺"是地块与道路关系，wild 描述里的"临湖"是地形特征邻接——同一套 LLM 抽取 prompt 需要按 scene_type 切换 schema 约束和常识先验

## 5. 类别 C：通用图片

### 5.1 问题特点

与结构化图纸不同，通用图片（手机照片、实景照片、概念图）是**真实世界的光学投影**，不含现成的符号语义，需要从像素直接推断三维空间结构，核心困难是**深度/尺度歧义**（单张 2D 图片理论上对应无穷多种 3D 解释）和真实场景的遮挡/光照干扰。这一类内部按技术路线细分两条子路线（多视角重建路线交互成本过高，暂不纳入）：

### 5.2 子路线 A：分割/检测模型（传统 CV pipeline）

| 组件 | 代表方法 | 要点 |
|------|---------|------|
| 语义分割 | Segment Anything (SAM) + 语义分类头 | 先通用分割出区域，再分类 region_type |
| 单目布局估计（房间专用） | LayoutNet / HorizonNet（全景图输入） | 针对室内全景图，直接回归房间的地面/墙面/天花板边界，是单图室内布局估计的经典基线 |
| 单目深度估计 | MiDaS / Depth Anything | 补充深度先验，辅助把 2D 分割提升到近似 3D |
| 建筑物轮廓提取（urban） | 遥感/街景图像的建筑分割网络 | 街景照片场景可用，卫星图属于专业数据源已排除 |

- ✅ 每个环节可独立替换/调优，可解释性强
- ⚠️ pipeline 越长，误差累积越明显；深度估计在遮挡区域天然不可靠

### 5.3 子路线 B：多模态 LLM 端到端

| 方法 | 技术要点 | 现状 |
|------|---------|------|
| **多模态 LLM 直接输出结构化描述**（如 GPT-4V / Gemini / Claude 系列的视觉理解能力 + structured output） | 把图片直接喂给多模态模型，要求输出房间列表/大致边界/门窗位置的结构化 JSON | 定性理解（"这是客厅，有一张沙发朝电视"）已经比较可靠，但**精确几何坐标**（多边形顶点、门宽厘米级）不是多模态 LLM 的强项，通常只能给出粗略框或相对位置描述 |
| **多模态 LLM 做粗筛 + 专用模型做精修** | 先用多模态 LLM 判断场景类型、大致区域划分、物体清单，再把结果作为先验喂给分割模型做几何精化 | 工程上更实际的落地方式，兼顾语义理解力和几何精度 |

### 5.4 图像 + 文字联合输入（子路线 B 的增强模式）

子路线 B（多模态 LLM）天然支持图像和文字同时作为 prompt 输入，不需要额外训练新模型即可低成本获得增强效果：用户上传图片的同时补一句文字说明（如"这是客厅，大概 25 平，沙发对着电视墙"），文字能补充图像里缺失或歧义的信息（尺度、房间用途、看不清的角落），图像能补充文字里没描述到的具体形状——两者互相校正，比单独任一路线的信息量更大。

这不是独立于类别 B（自然语言描述）和类别 C（通用图片）之外的"第四类"，而是两者在用户愿意同时提供图文素材时的联合增强：本质仍是子路线 B 的一次多模态 LLM 调用，只是 prompt 里除了图片还多了一段文字。产品上可以作为可选项呈现（"想让识别更准确？补充一句描述"），不强制要求，符合"输入足够简单"的原则——纯图片依然是合法的最简输入，文字是可选的精度增强手段。

**输出仍必须是可编程的中间表示（SceneVector），不是图片**：无论输入是纯图片、纯文字、还是图文联合，本文档的立场是一致的——识别/生成算法的产出必须是结构化矢量数据，而非文生图模型直接产出的像素图。这一点和 LayoutGPT、Holodeck 的立场一致（见第 1 节相关工作）：像素图片无法被程序读取几何信息、无法做约束校验、无法支持局部编辑（编辑图片等于重新生成一张新图，不是对同一场景数据做修改）；只有结构化矢量才能承接 [unified-scene-pipeline](../unified-scene-pipeline/README.md) 第 4 节的约束校验和自然语言二次调整闭环。图文联合输入只是让"识别"这一步的初稿质量更高，不改变输出形态的要求。

### 5.5 子路线对比

| 子路线 | 输入成本（用户操作） | 几何精度 | 语义理解力 | 工程成熟度 |
|--------|-------------------|---------|-----------|-----------|
| A 分割/检测 | 单张照片 | 中（有深度歧义） | 中（依赖分类头覆盖的类别） | 高（成熟开源模型多） |
| B 多模态 LLM | 单张照片 | 低（坐标非强项） | 高（常识/语义理解强） | 中（API 现成，精度需验证） |

**现实落地建议**：A+B 组合（语义交给多模态 LLM 粗筛，几何交给专用分割模型精修）是短期最可行的路径。

> 多视角重建（SfM/NeRF + 3D 分割）路线几何精度更高，但要求用户环拍多张/录像，交互成本远高于"拍一张照片"，与"面向一般 C 端用户"的调研前提不符，暂不纳入。

## 6. 三大类横向对比

| 维度 | A. 结构化图纸/草图 | B. 自然语言 | C. 通用图片 |
|------|-------------------|------------|------------|
| 几何证据是否存在于输入本身 | 有（编码在符号里） | 无（需生成） | 有（编码在像素里，需解码） |
| 核心技术栈 | 检测/分割 + OCR | LLM 结构化生成 | 分割/多模态LLM/三维重建 |
| 输出几何精度上限 | 高（图纸本身精确） | 由生成模型的合理性决定，非"真实"精度 | 中～高（依赖是否多视角） |
| 主要失败模式 | 符号画风泛化性 | 几何非法/多解性 | 深度歧义、遮挡 |
| C 端可获得性 | 高（截图/手绘门槛低） | 最高（打字即可） | 高（拍照门槛低，环拍门槛稍高） |

三类共同的收尾步骤：无论走哪条路线，识别/生成出的原始结果都需要经过**几何合法性校验与归一化**（复用 `pipeline/utils/vector_normalize.py`），才能作为 `PipelineInput.scene_vector` 送入 `scene_understand`。
